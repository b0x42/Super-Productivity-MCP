# Timed scheduling and reminders on update_task

Adds two optional fields to `update_task`: `due_with_time` (sets SP's `dueWithTime`, clearing `dueDay` since SP treats the two as mutually exclusive) and `remind_at` (sets `remindAt`, the field SP's reminder selector watches for firing notifications). No plugin change is needed because `plugin.js`'s `updateTask` case already forwards its `data` object verbatim to `PluginAPI.updateTask` — verified by reading the handler. The schema correctly rejects combining `due_day` and `due_with_time` in the same call and allows `due_with_time: null` to clear, but `remind_at` cannot be cleared because SP's plugin API rejects a `null` value for it (typia validation on SP's side, not a choice made here).

Watch for: the one-way mutual exclusivity (confirmed) — setting `due_with_time` clears `due_day`, but setting `due_day` alone does not clear a pre-existing `due_with_time`, so a task scheduled with a time and later given a plain due day via a separate call can end up with both fields set in SP's store, a state the author's own PR description says SP's reducer never produces.

**Verdict**: APPROVED

## High-level view

The core mechanism is sound: the plugin's generic `updateTask` passthrough really does accept arbitrary fields, so routing `dueWithTime`/`remindAt` through the existing `data` object was the right call and no plugin change was required. The new Zod fields are nullable/non-nullable in the way SP's own API constraints demand, and the handler's mutual-exclusivity check correctly covers every combination tested, including the empty-string-due_day-plus-due_with_time edge case, which resolves correctly without needing a special case.

The gap is directional: the mutual exclusivity is enforced only within a single call, not against the task's existing state. A task that already has `dueWithTime` set and later receives a plain `due_day` update (without `due_with_time` in the same call) will carry both fields afterward, since nothing clears the old `dueWithTime`. This is a new failure mode this PR introduces, since `due_with_time` didn't exist as a settable field before.

The scoping choices — leaving `remind_at` non-clearable, and not touching `bulk_update_tasks` or `create_task` — are both reasonable and clearly disclosed in the PR body rather than hidden. The non-clearable limitation is a genuine constraint of SP's own plugin API, not a shortcut taken here.

### Plugin passthrough claim, verified

The PR description asserts no plugin change is needed because `updateTask`'s generic passthrough already supports arbitrary fields. Reading `plugin/plugin.js`'s `updateTask` case confirms this:

```js
case 'updateTask': {
  const updateData = command.data || {};
  if ('dueDay' in updateData && !('plannedAt' in updateData)) {
    const allTasksForUpdate = await PluginAPI.getTasks();
    const taskForUpdate = allTasksForUpdate.find(t => t.id === command.taskId);
    const currentPlannedAt = taskForUpdate ? (taskForUpdate.plannedAt ?? null) : null;
    result = await PluginAPI.updateTask(command.taskId, { ...updateData, plannedAt: currentPlannedAt });
  } else {
    result = await PluginAPI.updateTask(command.taskId, updateData);
  }
  break;
}
```

The claim holds, with one side effect worth knowing about: setting `due_with_time` to a non-null value makes the server add `dueDay: null` to the outgoing `data` (to enforce the mutual exclusivity SP itself keeps). That means every `due_with_time`-set call also has `'dueDay' in updateData` true, which trips the plugin's plannedAt-preservation branch and triggers an extra `getTasks()` round trip to look up and re-apply the current `plannedAt`. Functionally correct — `plannedAt` and the due/time fields are meant to be independent — but it's an unannounced extra IPC round trip on every `due_with_time`-set call, worth being aware of if IPC latency ever becomes a concern.

### One-way mutual exclusivity between `due_day` and `due_with_time`

The handler's guard only looks at what's in the *current* call:

```ts
if (due_with_time != null && due_day) {
  return errorResult('due_day and due_with_time are mutually exclusive — pass only one');
}
...
if (due_with_time !== undefined) {
  data.dueWithTime = due_with_time;
  if (due_with_time !== null) data.dueDay = null;
}
```

Setting `due_with_time` always clears `due_day` in the same payload. But the reverse never happens: a call with only `due_day` set (`due_with_time` omitted entirely) leaves any existing `dueWithTime` on the task untouched. Sequence: call 1 sets `due_with_time: X` (clears `dueDay`); call 2 sets `due_day: 'Y'` without mentioning `due_with_time` at all. After call 2 the task has both `dueDay: 'Y'` and `dueWithTime: X` in SP's store — the exact combination the PR describes SP's own `scheduleTaskWithTime` reducer as preventing. This is new behavior enabled by this PR (the `due_with_time` field didn't exist before), not a pre-existing limitation being extended. It's a narrow sequence (two separate calls, not one), the existing tests only cover the single-call combinations (both passed together → rejected; `due_with_time: null` + `due_day` → switches cleanly), so there's no test either confirming or ruling out the cross-call case.

Fix would be symmetric and small: when `due_day` is set (truthy) and `due_with_time` wasn't passed in the same call, also clear `data.dueWithTime = null`. Given the fix is cheap and the inconsistency is real, this seems worth doing in this PR or as an immediate fast-follow rather than carrying it as a silent gap.

### Schema strictness is new for timestamp fields in this file

`due_with_time` and `remind_at` are `z.number().int().positive()`, while the existing `planned_at` field (same category — Unix ms timestamp, same file) is just `z.number()`. Not wrong, arguably stricter is better, but it's a new validation convention introduced only for these two fields rather than applied consistently. Harmless given these timestamps are always positive integers in practice, just worth noting as something a future field would need to decide to follow or not.

### Scoping decisions

Leaving `remind_at` non-clearable is a real constraint of SP's plugin API (typia rejects `null` for that field), not something this PR chose to skip — reasonable to ship as-is with the limitation documented. Not extending `bulk_update_tasks` and `create_task` to the same two fields is also reasonable: the PR is scoped to the concrete need (schedule-with-reminder via `update_task`), and the author explicitly offers to extend the surface if wanted rather than silently leaving it inconsistent. Neither should block merge.

### Test coverage

The four new behavioral tests cover the real cases well: set both fields together, clear `due_with_time` with `null`, switch from timed to day-based, and reject the same-call conflict. The two schema tests (`accepts due_with_time and remind_at`, `rejects a null remind_at`) match the new validation shape. Missing: a test for `remind_at` set in isolation (not combined with `due_with_time`), and nothing exercises the cross-call `due_day`-after-`due_with_time` sequence described above — understandably, since it would currently demonstrate the gap rather than confirm correct behavior.
